# 老年多轮闲聊双 Agent 优化 Goal 澄清问题

## Codex `/goal` 使用形式理解

`/goal` 适合用来定义一个可持续执行的明确目标，而不是临时任务描述。目标需要尽量包含：

1. 明确 objective：要把这个库改造成什么状态。
2. 范围边界：哪些文件、模块、流程会被改，哪些暂不改。
3. 验收标准：哪些行为、测试、指标证明目标完成。
4. 约束条件：延迟、风险、记忆真实性、老人陪伴语气、兼容现有接口等。
5. 阻塞条件：哪些问题必须由你确认后才能继续。

这个库当前对应关系大致是：

- Agent A：`src/agents/dialogue_agent.py` 的 `generate_initial_reply` / `generate_initial_reply_stream`，以及 `prompts/dialogue_agent.md` 中的即时回复规则。
- Agent B：`src/agents/memory_retrieval_workflow.py` 的记忆选择，加上 `generate_followup_reply` / `prompts/dialogue_followup_decision.md` 的二次回复决策。
- Orchestration：`src/services/dialogue_service.py` 中同步 `/chat` 和流式 `/chat/stream` 的请求绑定、后台检索、follow-up 生成与事件发布。
- 测试基础：`tests/test_dialogue_agent.py`、`tests/test_memory_retrieval_workflow.py`、`tests/test_dialogue_service.py`、`tests/test_latency_benchmark.py` 已经使用 fake model / fake store 做可复现测试。

## 目标草案

把现有长期记忆聊天 Demo 优化成面向老年用户多轮闲聊的低延迟双 Agent 回应流程：Agent A 在用户说完后先输出 1-2 句温和、自然、低风险的即时承接话，不主动展开完整答案，也不编造记忆；Agent B 在 Agent A 输出期间并行完成记忆检索和个性化续接生成，只使用检索到的真实记忆，在需要时产出与 Agent A 自然衔接的第二段回应，引导老人继续聊天。同步更新 prompt、orchestration 和可复现测试样例，覆盖衔接自然度、记忆使用准确性、情绪接住质量、风险控制和延迟表现。

## 请你确认的问题

1. Agent A 的即时回复长度要如何硬性约束？
   例如按中文句子数限制为 1-2 句，还是按字数限制为 15-40 字，或者两者都限制。

   感觉1-2句比较好，不限制字数。但是要确保agent b 能接上。

2. Agent A 是否必须始终以 `[emo:key][act:key]` 开头？
   `data/Model.md` 现在要求每次回复开头带情绪和动作 tag，但低延迟自然闲聊可能会受 tag 影响，需要确认测试中是否也强制校验。

   是的，甚至每个回复都必须。

3. Agent A 的“留出续接空间”具体表现是什么？
   例如只接住情绪和话题，不主动问太具体的问题；还是可以问一个轻量问题，但不能提前引用记忆。
   我感觉不能问问题，或者问了也没关系，但是不能和B相矛盾或者差距很大。

4. Agent A 面对高风险内容时的最低安全策略是什么？
   例如身体不舒服、用药、摔倒、财务转账、法律纠纷时，是否要求即时回复必须包含“建议联系医生/家人/专业人士”等固定意图。

   如果是极为危险的，肯定是联系家人。或者调用相关的报警api，然后拦截b的输出之类的（这个可以留空），但是对于问是否需要吃药，A负责说让我想想，然后B查看记忆比如记忆最近有没有吃药后提供回复。

5. Agent B 的输出应该作为独立 follow-up 事件展示，还是最终要在客户端表现为同一轮回答的第二段？
   当前库里 follow-up 是独立事件和独立 assistant turn，需要确认是否保留这个数据结构，只优化文案衔接。 目前结构是对的，但是它可能作为同一轮回答的第二段或者下一轮回复中的插入，其实是更希望它马上就可以回复。

6. Agent B 的第二段长度期望是多少？
   例如 1-2 句、30-80 字，还是允许更长的回忆引导。
    不是引导不引导的问题，就是带着记忆陪人聊天，本来我们没有这个双轮机制，但是如果没有的话，第一轮的回复就需要阅读记忆，等待非常久，我们才设计这个接住机制。

7. Agent B 是否一定要生成第二段？
   当前设计允许 `no_followup`，需要确认在老人闲聊场景下，检索到相关记忆时是否默认积极续接，检索不到时是否必须静默。
   不一定，有些问题，比如老人跟机器人打招呼，显然不用。

8. Agent B 引用记忆的表达边界是什么？
   例如可以说“我记得你之前提过...”，还是要更含蓄地说“你之前说过...”；是否需要避免让老人觉得被监控。 非常需要到，甚至可以说，老人说：

我小时候可贪玩了。

不好的 A：

哈哈，您小时候一定特别活泼，贪玩也是童年的快乐呀，那时候没有手机电脑，大家都在外面跑来跑去，想想就很有意思。

这个太满了，B 再接记忆就突兀。

更好的 A：

哈哈，听起来您小时候一定很有活力呀。
那会儿是不是经常一玩起来就忘了回家？

这段既接住了情绪，又留出了继续展开的空间。这种，老人记忆里面有不回家的记忆事件。一定不能古板，而且这些回复设计需要越灵活越像真人越好。

9. 记忆真实性的验收标准怎么定？
   例如测试需要校验 Agent B 回复只包含 retrieved memory 中存在的事实，不能使用 lightweight memory 未完整加载的内容，也不能从 User.md 推断成具体事件。

   这个倒不是很重要，我关注的是回复效果（指是不是真的懂老人以及能引起老人继续回复的兴趣）

10. 记忆冲突或过期时怎么处理？
    如果 retrieved items 中有 `valid_until` 过期、`confidence` 低、或内容互相冲突，Agent B 是不回复、提示不确定，还是只使用最新/最高置信度记忆。

    这个目前我都是交给agentB的第一轮模型去判断，模型很聪明，能从这些记忆（带有日期的行为）中判断，目前不用过于考虑，我们后期会考虑这些问题。

11. 多轮闲聊测试样例需要覆盖哪些老人画像？
    例如独居老人、和子女同住老人、退休教师、慢病老人、丧偶老人、健谈老人、沉默/情绪低落老人等。
    什么都有可能啊，这种不能限制死了。

12. 测试案例数量期望是多少？
    建议至少分三层：单元测试 8-12 个、orchestration 测试 4-6 个、端到端样例集 10-20 条。你希望一次 goal 内做到哪个规模。

    要么我给你的api显示消耗殆尽，要么就是尽可能的高，80%左右的测试通过率吧。

13. 测试案例应该写成 unittest 代码、JSON/Markdown golden cases，还是两者都要？
    当前仓库主要是 `unittest`，但衔接自然度和记忆准确性可能更适合额外维护一份可读样例集。
    测试样例不是看是否检测相关记忆，是看能不能维护好一段对话，所有的测试都必须是这种。然后我需要你调用模型打分，你需要从各个角度对这个打分，我会提供apikey，你包装好。

14. 衔接效果如何自动化评估？
    例如用规则校验：Agent A 不含记忆事实、Agent B 含目标记忆事实、第二段不开头重复问候、不否定第一段、不突兀切题；还是引入 LLM judge 脚本作为手动评测。
    A是否能合理引入B，B1是否正确判断需要进行第二轮回复，B2是否给到了很足的情绪价值，并且符合老年人的设定要求。引入 LLM judge 脚本作为手动评测，多个方面。

15. 情绪接住质量如何表现和测试？
    例如测试“孤独、身体不舒服、回忆往事、抱怨子女、普通家常、重复表达”等场景，校验 Agent A 必须先回应情绪，再轻轻承接话题。

16. 延迟目标要用什么指标？
    例如 Agent A 首 token 小于 800ms、完整 Agent A 小于 1500ms、Agent B 在 Agent A 播放结束前完成的比例达到某个阈值；如果没有真实模型稳定指标，是否只做可控 fake 延迟测试。 对于A暂时不用管，就是A回答完后（不正式启用audio部分，按照每个token 300毫秒的速度，测算时间），然后B2在A之后1s内给出结果算成功。（对于80%的测试样例）

17. Orchestration 的优化边界是什么？
    当前流式模式是在 initial reply 完成后才调度后台 retrieval；你的目标是让 memory retrieval 在 Agent A 开始输出后立刻并行，还是在用户消息进入后、Agent A 调用前就启动检索。
    应该是A\B同时启动，然后B返回启动B2。

18. 是否允许调整 API / SSE 事件协议？
    例如新增 `agent_a_done`、`agent_b_ready`、`followup_delta`、`latency_metrics`，还是必须兼容当前 `meta`、`delta`、`done`、`followup`。这些部分必须坚持已有的，最好只是补充，因为还有同事在做其他部分开发，我只是拉了个分支。

19. 真实模型调用测试是否纳入目标？
    当前全量测试不跑真实模型，`scripts/latency_benchmark.py` 是手动 benchmark。这个 goal 是否需要新增真实模型 smoke/benchmark 命令，还是只保证离线 fake 测试可复现。

    肯定真实模型结果需要测试，我会提供文本生成的api。但是禁用tts、stt等模块，也不许修改相关代码。

20. 这次 goal 的完成物希望包括哪些文档？
    例如只要代码和测试，还是同时更新 `README.md`、`docs/api_contracts.md`、prompt 文档、测试样例说明和一份评估报告模板。
    修改内容包括代码、prompt、文档等（不限于此）。但是需要提供所有的修改内容（最终版本），一份benchmark、案例结果等。另附送一个我其它的尝试：

    这是个1轮的对话，模拟了与史铁生的对话并且带有史铁生本人的记忆模仿：
    Q:我再问你一个问题，很重要!我认为百事可乐比可口可乐好喝很多，有很多人不同意，你怎么看?百事还是可口可乐，别装理中客:

    A:哈哈，这事儿我可真不是装一-我是真说不好。
    我那会儿能喝上一瓶北冰洋汽水就高兴半天了，可乐这玩意儿，我喝过，但没你们喝得那么讲究。让我在百事和可口之间站个队，跟让我在两种我分不清的甜水之间选一个似的，你饶了我吧。
    不过你这问题有意思的不是答案，是那个"很多人不同意"。
    你想啊-一杯糖水而已，配方差那么一点点，颜色一样，气泡一样，喝下去不过几秒钟的事儿。可人就为这个能争。这说明什么?说明人争的从来不是那杯水，是"我的舌头我做主"那点儿东西。是"凭什么你说好喝就是好喝"那点儿不服气。

    所以你爱百事，你就爱百事--爱得理直气壮些，别让那"很多人"把你说服了。舌头是你自己的。

## 等你回答后可收敛的正式 `/goal` 模板

```text
/goal objective:
优化本仓库的老年多轮闲聊双 Agent 回应流程，使 Agent A 负责低延迟、短句、温和、低风险承接，Agent B 负责基于真实检索记忆的个性化续接，并通过 orchestration 让记忆检索/生成尽量与 Agent A 输出并行完成。实现后必须有可复现测试样例验证衔接自然度、记忆真实性、情绪接住质量、风险控制和延迟表现。

scope:
- 更新 Agent A / Agent B prompt 与必要的输出规范。
- 优化 `src/services/dialogue_service.py` 的流式编排，使检索尽早并行。
- 增加或调整 `tests/` 中的 fake 模型、fake 记忆、orchestration 测试。
- 增加可读的评估样例集和延迟评测入口，具体格式等待澄清后确定。

acceptance:
- Agent A 测试证明即时回复短、自然、不含 retrieved memory、不编造记忆。
- Agent B 测试证明只使用 retrieved full memory，不使用不存在或未加载的记忆事实。
- Orchestration 测试证明 Agent B 检索与 Agent A 流式输出并行，且 request_id/turn_id 绑定正确。
- 样例测试覆盖多类老人闲聊场景，并能复现两段回复的自然衔接。
- 延迟测试至少能用 fake timing 稳定验证编排不等待 Agent B 才完成 Agent A。
```
